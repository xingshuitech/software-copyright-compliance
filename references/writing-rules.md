# 工程记录式写作与降重规则

## 合规边界（先读）

2026 年 3 月 15 日起，新版申请表签章页要求申请人声明未使用 AI 开发编写代码、撰写文档或生成登记申请材料。因此：

- 本文件涉及的「降重」「去模板味」，目的只能是让材料回到真实开发事实，不是掩盖内容来源。
- 助手起草的段落，申请人签署前必须逐字核实，按真实情况改写或确认。
- 不虚构日期、命令输出、测试结果、人员、单位和技术指标。
- 不把不存在的开发过程补写成流水记录。没有 Git 历史就写「无版本库」，不编造提交。

## 判断标准

送审材料不是宣传稿。审查关注的是材料之间是否一致、内容是否能被源码支撑、格式是否符合规范。文字「像不像人写」不是靠换同义词解决的，而是靠写具体对象、具体动作、具体结果解决的。

## 必须写进去的内容

优先写以下六类事实：

1. 真实文件名和目录名，例如 `src/pack.js`、`bin/tool.js`、`web/template.html`。
2. 实际执行过的命令及返回，例如 `npm test` 三档通过、`git rev-parse --show-toplevel` 无输出。
3. 实测数值，例如源码行数、手册页数、每页行数、算法参数取值。
4. 真实报错原文，例如 `ModuleNotFoundError: No module named 'PIL'`。
5. 具体修复动作，例如把工具集版本改成 14/29、用 `pypdf` 清空 `/Producer`。
6. 明确的边界，例如「函数级打包在 ZTS 下未启用」，不写「已全面支持」。

## 不要写进去的内容

以下写法会立刻暴露模板味，直接删除：

- 「本软件本着……原则」「随着信息技术的不断发展」「为用户提供了良好的体验」
- 「经过反复测试，性能优越，稳定可靠」「具有广阔的应用前景」
- 「本项目采用先进的架构」「实现了全方位的保障」
- 目录页、术语表、一致性核对表、功能对照表、成段的元叙述
- 把 `.md` 文档列成成果清单。内部笔记不是交付物，不要写进送审材料
- 工整到失真的四字并列：「安全高效、简洁易用、功能强大、稳定可靠」
- 无法核验的结论：「原创算法」「国内领先」「不可破解」「100% 兼容」

## 句式

用短句，主语多为「我」或省略，动词用完成态：

```text
11-04 后半夜，先解决编译环境。
工具集版本不对，patch 成 14/29 后才能链接。
常量操作数改成字面量索引编码，地址变化不再影响解码。
运行 npm test，tier1 到 tier3 全部 PASS。
```

避免：

```text
在这一阶段，我们主要围绕编译环境进行了系统性的优化工作，
通过引入一系列改进措施，有效提升了整体的稳定性与可靠性。
```

## 口径分离

同一件事在用户手册和源程序鉴别材料里可以写法不同，但事实不能冲突。

- 用户手册、申请表：写对外版本，例如 `V1.0`、`22.x`、`8.x`。
- 源程序鉴别材料：逐字反映源码，保留内部版本常量、调试开关、构建代号和对内部说明文档的引用。
- 开发过程记录：按实际情况写记录人员和单位，例如 `记录人员：某某`、`单位：某某公司`。
- 著作权人署名：只写软件名称时不署个人；不要把记录人员误写进著作权人字段。

不要为了「像人写」去改源码注释里的版本号、调试开关、报告字符串。那是鉴别材料，必须如实反映源码。只改真正的编辑残留，比如注释末尾多出的 `.)`，并且必须同步改源码、重新测试、重新生成鉴别材料。

## 降重做法

- 同一参数只在一处展开说明，其他材料交叉引用时写简短结论。
- 用不同的观察角度：用户手册写操作和结果，算法说明写取舍和参数，开发记录写时间和错误。
- 用实测数据替代形容词。写「每页 52–56 行」比写「排版规范」有效。
- 保留技术边界。写「主脚本内部函数调用暂不支持」比写「支持所有常见场景」更可信。
- 不要为了凑行数重复同一段话，补充真实实现细节即可。

## 技术特点写法

写「自行设计的部分」，但不要给无法验证的排他性结论。

可以写：

```text
标识符重命名按作用域绑定逐项生成；字符串逐串独立派生密钥；
解包层的状态规模、取流顺序和完整性门限由本地随机状态决定。
```

不要写：

```text
采用全球领先的原创加密算法，破解难度极高，安全性达到国际先进水平。
```
